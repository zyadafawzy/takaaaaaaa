# منصة سوبرماركت متعددة المتاجر — تنفيذ إنتاجي كامل

## النتيجة المطلوبة
كل متجر يعمل كنسخة مستقلة كاملة من المحرك، بدون ظهور اسم أو شعار تِكّة وبدون أي رابط يعيد العميل إليها. المسار المعتمد الآن:

```text
/s/{storeSlug}                 واجهة المتجر
/s/{storeSlug}/product/{slug}  المنتج
/s/{storeSlug}/cart            السلة
/s/{storeSlug}/checkout        الدفع
/s/{storeSlug}/order/{token}   تأكيد الطلب
/s/{storeSlug}/track/{token}   المتابعة
/s/{storeSlug}/admin/...       لوحة إدارة المتجر
```

تظل تِكّة نفسها متجرًا رئيسيًا مستقلًا على `/` و`/admin`، لكن لا تظهر داخل أي متجر آخر.

## 1. عزل المتجر من أول الزيارة حتى الطلب
- إنشاء `StoreRuntimeContext` يحمل `storeId`, `slug`, الهوية، التواصل، إعدادات الطلب، الفروع ومناطق التوصيل.
- جعل السلة منفصلة لكل متجر بمفتاح تخزين يحتوي `storeId`، ومنع خلط منتجات متجرين.
- إضافة جميع مسارات السلة والدفع والطلب والمتابعة تحت `/s/$storeSlug` وإبقاء المستخدم داخل المتجر دائمًا.
- تمرير `storeId` صراحة إلى تسعير السلة وإنشاء الطلب؛ الخادم يتحقق أن كل منتج/سعر/مخزون متاح لهذا المتجر.
- كتابة `store_id` على السلة والطلب، واستخدام رقم واتساب واسم وعنوان وفروع ومناطق توصيل المتجر نفسه.
- إرجاع روابط المتابعة والسياسات والرئيسية إلى نفس المتجر، مع metadata وfavicon وشعار واسم خاصين به.

## 2. كتالوج هجين: رئيسي + منتجات خاصة
- الإبقاء على كتالوج المنصة الرئيسي مع تخصيص السعر، سعر المقارنة، المخزون، الظهور، الصور والترتيب لكل متجر.
- إضافة ملكية اختيارية للمنتج والتصنيف والعلامة: `owner_store_id = NULL` للمشترك، أو متجر محدد للخاص.
- تمكين مدير المتجر من اختيار المشترك وإنشاء منتجات وتصنيفات وصور خاصة لا يراها أو يعدلها متجر آخر.
- توحيد استعلام العرض بحيث يدمج المشترك المعيّن والخاص، مع السعر والمخزون الفعليين للمتجر.
- تحديث البحث والتوصيات والعروض والاستيراد لتلتزم بنطاق المتجر.

## 3. لوحة إدارة مستقلة لكل متجر
- بناء `/s/$storeSlug/admin` بنفس قوة لوحة تِكّة: نظرة عامة، الطلبات، الكتالوج، المنتجات الخاصة، المخزون، العروض، التوصيل، الإعلانات، الإعدادات، التقارير والمستخدمون.
- ربط المستخدمين عبر `store_users` بدور `store_admin` أو `store_staff`، والتحقق من المتجر والدور على الخادم وفي RLS لكل عملية.
- إضافة خطوة “مدير المتجر” إلى معالج الإنشاء: البريد، الاسم، الدعوة/إنشاء حساب آمن، وربطه بالمتجر.
- مالك المنصة يستطيع دخول أي متجر؛ مدير المتجر لا يرى إلا متجره.
- حذف مسار الدخول المحلي `admin_session` والحساب الصلب `zizo-admin`؛ المصادقة الوحيدة Supabase Auth والصلاحيات من قاعدة البيانات.

## 4. Themes وهوية واتصال أوسع
- توسيع الهوية لتشمل: شعار، favicon، 12+ قالب جاهز، الوضع الفاتح/الداكن، الخط، نصف قطر العناصر، كثافة العرض، نمط الهيدر، شكل بطاقات المنتجات، banner/hero، وألوان الحالات.
- معاينة حية حقيقية لكل القالب، مع فحص تباين ومنع حفظ لون غير صالح.
- إعدادات اتصال مستقلة: هاتف، واتساب الطلبات، الدعم، بريد، عنوان، ساعات العمل، روابط اجتماعية وفروع متعددة.
- إعدادات الطلب المستقلة: قبول/إيقاف الطلبات، استلام، توصيل، حد أدنى، سياسة الاستبدال، نص واتساب، وسائل الدفع المتاحة ورسائل الحالة.
- حفظ كل ذلك كبيانات المتجر، لا قيم ثابتة داخل الواجهة.

## 5. قاعدة البيانات والأمان
- تعديل RLS على `orders`, `order_items`, `order_events`, `order_notes`, `anonymous_carts`, `cart_items`, المخزون والكتالوج ليكون الوصول بـ `user_can_access_store(auth.uid(), store_id)`؛ المستخدم العام لا يحصل على وصول إداري.
- إضافة علاقات وفهارس مركبة تبدأ بـ `store_id` للاستعلامات المتكررة، مع uniqueness داخل المتجر حيث يلزم.
- إنشاء دوال معاملات آمنة لإنشاء متجر وإعداداته وربط المنتجات ومناطق التوصيل بشكل ذري، مع سجل نشاط واضح.
- إصلاح تحذيرات الأمان المرتبطة بالدوال `SECURITY DEFINER` ومنع تنفيذها من أدوار غير لازمة، ثم تشغيل linter واختبارات عزل متجرين.

## 6. الـ limit والتوسع الصحيح
المشكلة ليست “عدد columns”؛ قاعدة البيانات الحالية فيها آلاف الصفوف بالفعل. رفع حد الاستجابة عالميًا إلى رقم ضخم سيبطّئ المنصة ويستهلك الذاكرة، ولن يكون مناسبًا لآلاف المتاجر. التنفيذ القوي سيكون:
- لا يوجد حد إجمالي لعدد المنتجات أو الطلبات أو المتاجر المخزنة.
- Pagination/cursor لكل القوائم، مع تحميل دفعات قابل للزيادة بدل قص البيانات عند 500/600/1000.
- إزالة الاستعلامات التي تسحب كل الطلبات أو كل تعيينات المتاجر لحساب الإحصائيات، واستبدالها بتجميعات SQL وفهارس.
- دعم bulk operations على دفعات آمنة، والبحث الخادمي، وعدادات دقيقة بدون تحميل الصفوف للمتصفح.
- مراجعة query plans والاستعلامات البطيئة بعد التنفيذ.

## 7. ترتيب التنفيذ والتحقق
1. Migration للعزل والكتالوج الهجين والإعدادات والفهارس والسياسات.
2. Store runtime + السلة والدفع والطلبات والمتابعة كاملة داخل مسار المتجر.
3. إدارة المتجر والمستخدمين والصلاحيات وإزالة أي bypass محلي.
4. توسيع themes والتواصل والفروع وإعدادات الطلب.
5. تحديث لوحة المطوّر ومعالج الإنشاء ليُنشئ متجرًا جاهزًا فعليًا.
6. اختبارات E2E بمتجرين: شعاران مختلفان، سلتان، سعران، طلبان، واتسابان، ومديران؛ محاولة كل مدير فتح بيانات الآخر يجب أن تفشل.
7. اختبار responsive، metadata، أخطاء المتصفح، linter، وأداء القوائم الكبيرة.

## ملاحظات تقنية
- الاختيار المعتمد: **مسار مستقل** لكل متجر، و**كتالوج مشترك + منتجات خاصة**.
- لن نكرر واجهة تِكّة في ملفات منفصلة؛ سنعيد استخدام المحرك نفسه تحت سياق متجر إلزامي حتى تظل آلاف المتاجر قابلة للصيانة.
- لن نرفع حد API عالميًا بلا سقف؛ سنزيل أي قص وظيفي عبر pagination واستعلامات مجمعة، وهو الحل الصحيح للتوسع.
